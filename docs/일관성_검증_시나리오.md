# 종단 재고 일관성 검증 시나리오

RTL-H 핵심 10번(실시간 동기화 신뢰성)의 "종단간 재고 일관성 검증 시나리오"에 해당하는 문서다.
자동화된 판정은 `scripts/verify_omni.py`가 수행하며, 이 문서는 각 시나리오의 의도·경로·판정 기준을 정의한다.

## 검증 대상 경로

```
온라인 경로:  주문 생성(가용 확인) → 모의결제(조건부 차감) → 재고 원장 → 상품 응답 오버레이
오프라인 경로: 가상 POS DB(binlog) → Debezium 소스 커넥터 → Kafka → pos-sync 컨슈머 → 재고 원장
정산 경로:    Kafka → JDBC Sink 커넥터 → 가상 정산 DB(pos_stock_ledger)
```

세 경로가 모두 하나의 재고 원장(stock-service)으로 수렴하므로,
일관성 판정 기준은 항상 "원장 값과 각 끝단의 값이 일치하는가"이다.

## 사전 조건

- `docker compose up -d` 로 인프라 기동, 서비스 8종 정상 등록 (유레카 6개 도메인 서비스 확인)
- CDC 커넥터 2종(pos-source, settlement-sink) RUNNING
- 재고 원장은 기동 시 상품 카탈로그 490건 기준으로 초기화됨

## 시나리오 1. 온라인 주문 경로 일관성

| 단계 | 행위 | 기대 결과 |
|---|---|---|
| 1 | 상품 5번 원장 조회 (`GET /stock-service/stocks/5`) | onlineStock = N |
| 2 | 수량 2 주문 생성 | 201, 상태 PENDING (생성 시 가용 확인 통과) |
| 3 | 모의결제 | 200, 상태 PAID |
| 4 | 원장 재조회 | onlineStock = N-2 |
| 5 | 상품 목록 조회 (`GET /product-service/products`) | 5번 상품 stock = N-2 (오버레이 일치) |

판정: 차감은 결제 시점에만 일어나고, 원장·상품 응답이 같은 값을 보여야 한다.

## 시나리오 2. 초과주문 방지 (2단 방어)

| 단계 | 행위 | 기대 결과 |
|---|---|---|
| 1 | 가용 재고를 초과하는 수량(99999)으로 주문 생성 | 409 INSUFFICIENT_STOCK (1차 방어: 생성 시 동기 확인) |
| 2 | 가용 전량으로 주문 생성 | 201 (확인 통과) |
| 3 | 다른 채널이 1개 선차감 (`PUT /stocks/5/deduct`) | 200 |
| 4 | 2의 주문을 결제 | 409 OUT_OF_STOCK + 주문 CANCELLED (2차 방어: 조건부 UPDATE) |
| 5 | 선차감분 복구 | 원장 원상 복귀 |

판정: 생성 시 확인과 결제 시 조건부 차감(`WHERE online_stock >= qty`)이 각각 독립적으로 초과주문을 막아야 한다.
확인과 결제 사이의 경합은 4단계가 재현한다. 다품목 결제 중 일부 실패 시에는 이미 차감된 품목을 보상 복구한다.

## 시나리오 3. POS 변경 → 원장 반영 (CDC)

| 단계 | 행위 | 기대 결과 |
|---|---|---|
| 1 | 동기화 현황 조회 (`GET /pos-sync-service/status`) | appliedCount = A |
| 2 | POS DB 직접 변경 (`UPDATE pos_stock SET stock = V WHERE product_id = 3`) | binlog 이벤트 발생 |
| 3 | 10초 내 원장 조회 | posStock = V |
| 4 | 동기화 현황 재조회 | appliedCount > A, dlqCount 증가 없음 |

판정: 반영은 after 절대값 세팅이므로 같은 이벤트가 중복 소비되어도 결과가 같다(멱등).
같은 값으로의 UPDATE 는 binlog 이벤트를 만들지 않으므로 검증 시 항상 이전과 다른 값을 쓴다.

## 시나리오 4. 원장 → 정산 DB (JDBC Sink)

| 단계 | 행위 | 기대 결과 |
|---|---|---|
| 1 | 시나리오 3 수행 직후 정산 DB 조회 (`SELECT stock FROM pos_stock_ledger WHERE product_id = 3`) | V (POS 변경값과 일치) |

판정: 소스(POS) → Kafka → Sink(정산)까지 같은 변경분이 도달해야 종단 일관성이 성립한다.

## 시나리오 5. 장애 주입 — DLQ 와 재소비 (수동 절차)

자동 검증 범위 밖이라 수동으로 수행한다.

1. 역직렬화가 불가능한 메시지를 `zeropick.pos.pos.pos_stock` 토픽에 직접 발행한다
   (`kafka-console-producer` 로 임의 문자열 전송).
2. pos-sync 로그에서 3회 재시도 후 DLQ(`zeropick.pos.dlq`) 발행을 확인한다.
   `GET /pos-sync-service/status` 의 dlqCount 가 1 증가한다.
3. 정상 이벤트는 계속 처리되는지 확인한다 (poison 메시지가 파이프라인을 막지 않아야 한다).
4. pos-sync 를 재시작한 뒤 POS 값을 다시 변경한다. 오프셋 이후부터 정상 소비되고,
   재시작 전 마지막 이벤트가 재소비되어도 절대값 반영이라 원장 값은 변하지 않는다.

## 자동 검증 스크립트 매핑

`python scripts/verify_omni.py` 24항목 중 본 문서 해당 항목:

| 시나리오 | 스크립트 섹션 |
|---|---|
| 1 | 2번(원장·오버레이), 3번(주문 파이프라인) |
| 2 | 5번(초과주문 2단 방어) |
| 3 | 8번(POS 변경 → posStock, 카운트 증가) |
| 4 | 8번(JDBC Sink → 정산 DB) |
| 5 | 수동 절차 (위 참조) |

실행 결과 기록은 `docs/측정리포트.md` 에 남긴다.
